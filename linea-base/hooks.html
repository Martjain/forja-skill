Hooks: reglas que siempre se cumplen

Un hook es un comando tuyo que Claude Code ejecuta automáticamente en momentos concretos de su ciclo de vida: antes de usar una herramienta, después de editar un archivo, cuando necesita tu atención, cuando termina de responder…

La documentación lo resume así: los hooks dan control determinista. Ciertas acciones siempre ocurren, en vez de depender de que el modelo decida hacerlas.

¿Por qué no basta con pedírselo a Claude en el prompt o en CLAUDE.md?

📝 Instrucción (CLAUDE.md / prompt)

“Por favor, formatea con Prettier después de editar.” El modelo probablemente lo hará… pero es una sugerencia que puede olvidar.

vs

⚓ Hook

Un PostToolUse que ejecuta Prettier tras cada Edit/Write. Lo ejecuta Claude Code, no el modelo: ocurre siempre.

Usos típicos: formatear código tras editar, bloquear comandos peligrosos, proteger archivos sensibles, recibir una notificación cuando Claude te necesita, reinyectar contexto tras compactar, auditar cambios de configuración.

02 · EL CICLO DE VIDA¿Cuándo se dispara cada hook?

Los eventos ocurren a tres ritmos: por sesión, por turno y por cada llamada a herramienta. Pulsa ▶ Reproducir un turno para ver el recorrido, o haz clic en cualquier evento para ver su ficha. La etiqueta bloquea indica que el hook puede detener la acción.

FLUJO PRINCIPAL DE UNA SESIÓN
↺ PreToolUse → herramienta → PostToolUse se repite por cada herramienta que Claude use dentro del turno. Todo el turno se repite por cada prompt.
EVENTOS “LATERALES” (ocurren cuando toca)
Pulsa reproducir o haz clic en un evento.
La referencia oficial enumera más de 30 eventos (incluidos SubagentStop, TaskCreated, CwdChanged, FileChanged, WorktreeCreate, PreModelSwitch, Elicitation…). Aquí ves los más útiles para empezar; el resto sigue el mismo patrón.

03 · ANATOMÍATres niveles anidados

Todo hook vive dentro de la clave "hooks" de un archivo de configuración (settings.json). La estructura siempre tiene tres niveles: evento → grupo con matcher → manejadores. Pasa el ratón por cada capa.

1 · Evento

PostToolUse: cuándo. El nombre del momento del ciclo de vida. Cada evento es una clave dentro del único objeto hooks.

2 · Matcher

"Edit|Write": filtro. En eventos de herramientas filtra por nombre de herramienta. Vacío u omitido = siempre.

3 · Manejadores

La lista hooks interna: qué ejecutar. Puede haber varios; todos los que coinciden se ejecutan en paralelo.

type + command

"type": "command" ejecuta un comando de shell. Campos opcionales: timeout (segundos), if, statusMessage…

Error típico: si tu settings.json ya tiene una clave hooks, añade el nuevo evento como hermano de los existentes; no reemplaces todo el objeto. Y recuerda: el JSON no admite comas finales ni comentarios.

04 · PASO A PASOTu primer hook: aviso cuando Claude te necesita

Es el ejemplo con el que empieza la guía oficial: una notificación de escritorio cada vez que Claude espera tu respuesta o un permiso, para que no tengas que vigilar la terminal.

① Edita ~/.claude/settings.json

Si el archivo no existe, créalo. Elige tu sistema:

~/.claude/settings.json

② Verifica con /hooks

Escribe /hooks en el prompt de Claude Code. Se abre el navegador de hooks y el tuyo aparece bajo Notification.

③ Pruébalo

Pulsa Esc para volver. Pide a Claude algo que necesite permiso y cambia a otra ventana: deberías recibir la notificación.

④ Afínalo con el matcher

"matcher": "" dispara con todos los tipos de notificación. Para limitarlo:

MATCHERSE DISPARA CUANDO
permission_promptClaude necesita que apruebes una herramienta (tras ~6 s esperando)
idle_promptClaude terminó hace ~60 s y no has escrito nada
auth_successSe completa la autenticación
💡 También puedes describirle a Claude en la CLI el hook que quieres y pedirle que lo escriba por ti.

06 · CÓDIGOS DE SALIDATres respuestas posibles

El código con el que termina tu script decide qué pasa después. Haz clic en cada tarjeta.

0

La acción continúa. Ojo: en PreToolUse no significa “aprobado”: el flujo normal de permisos sigue aplicándose.

En UserPromptSubmit y SessionStart, el texto que imprimas por stdout se añade al contexto de Claude. Si stdout es un único objeto JSON, se interpreta como salida estructurada (sección 07).
2
Bloquear
clic para detalles
Error bloqueante: en los eventos que pueden bloquear, la acción se detiene. Escribe el motivo en stderr; según el evento se le envía a Claude como feedback (para que ajuste su enfoque) o se te muestra a ti.

En eventos que no pueden bloquear (p. ej. SessionStart), sólo se muestra stderr y todo continúa.
1, 3…
Error no bloqueante
clic para detalles
La acción sigue adelante y aparece un aviso <nombre> hook error en la transcripción con la primera línea de stderr.

Trampa clásica: exit 1 NO bloquea. Para hacer cumplir una política, usa exit 2.

¿A dónde va cada salida?

stdinJSON del evento que Claude Code te envía: session_id, cwd, hook_event_name, tool_name, tool_input…
stdoutCon exit 0: JSON de decisión, o texto que se añade al contexto (sólo en algunos eventos).
stderrCon exit 2: el motivo del bloqueo. Con otros códigos: aparece en el aviso de error.
Si varios hooks coinciden con el mismo evento, todos se ejecutan hasta el final y luego se combinan sus resultados. En PreToolUse gana la respuesta más restrictiva: deny > defer > ask > allow. Un deny no impide que un hook “hermano” (p. ej. uno que registra en un log) ya haya hecho su trabajo.

07 · SALIDA JSONCuando necesitas algo más fino que “sí / no”

Los códigos de salida sólo permiten bloquear o callar. Para más control: termina con exit 0 e imprime un único objeto JSON por stdout. Elige uno u otro enfoque por hook, no los mezcles.

Campo en el nivel equivocado = ignorado en silencio. Por ejemplo, permissionDecision y additionalContext van dentro de hookSpecificOutput. Si los pones en el nivel superior, el JSON se acepta pero no tiene efecto.

08 · MATCHERSProbador de matchers

Sin matcher, un hook se dispara en cada ocurrencia de su evento. Con matcher, sólo cuando coincide. Escribe un matcher y mira qué herramientas lo dispararían. Las reglas aplicadas son las de la referencia oficial.

HERRAMIENTAS DE EJEMPLO

Las 3 reglas

  • "*", "" u omitido → coincide con todo.
  • Sólo letras, dígitos, _, -, espacios, , y | → nombres exactos (o lista). "Edit, Write" equivale a "Edit|Write".
  • Cualquier otro carácter → expresión regular de JavaScript, sin anclar. mcp__memory__.* = todas las herramientas del servidor memory.
Los matchers distinguen mayúsculas: bash no coincide con Bash.

Un filtro más fino: el campo if

El matcher filtra sólo por nombre de herramienta. El campo if usa la sintaxis de reglas de permisos para filtrar por herramienta y argumentos, así el proceso sólo se lanza cuando coincide. Sólo funciona en eventos de herramientas.

sólo comandos git
ifCOMANDO BASH¿CORRE?
Bash(git *)git pushsí
Bash(git *)npm test && git pushsí cada subcomando se revisa
Bash(git *)echo $(git log)sí se revisa dentro de $()
Bash(git *)echo $(date)no
El filtro if es de “mejor esfuerzo”. Para reglas duras de permitir/denegar, usa el sistema de permisos, no un hook.

09 · UBICACIÓN¿Dónde guardo el hook?

El archivo donde lo pongas define su alcance. Las entradas de distintos niveles se suman, no se reemplazan. Haz clic en los anillos.

Para desactivar todos los hooks: "disableAllHooks": true en tu settings. Si editas los archivos con Claude Code abierto, el vigilante de archivos normalmente recoge los cambios solo.

12 · DEPURACIÓNCuando algo no funciona

🔇 El hook nunca se ejecuta
  • Ejecuta /hooks y confirma que aparece bajo el evento correcto.
  • Revisa que el matcher coincida exactamente (distingue mayúsculas).
  • ¿Evento correcto? PreToolUse es antes de la herramienta; PostToolUse, después.
  • Si el script no corre: hazlo ejecutable con chmod +x.
⚠️ Veo “PreToolUse hook error: …”
  • Tu script salió con un código distinto de 0 sin querer. Pruébalo a mano:
terminal
  • “command not found”: usa rutas absolutas o "$CLAUDE_PROJECT_DIR".
  • “jq: command not found”: instala jq o usa Python/Node para parsear.
📭 /hooks no muestra nada
  • Valida el JSON: sin comas finales ni comentarios.
  • Ubicación correcta: .claude/settings.json (proyecto) o ~/.claude/settings.json (global).
  • Si tras unos segundos no aparece, reinicia la sesión.
🧩 Mi JSON no tiene efecto
  • Texto extra antes del JSON: un echo en tu ~/.bashrc puede colarse en stdout y entonces la salida ya no empieza por {. Envuélvelo así:
~/.bashrc
  • Campo en el nivel equivocado: compáralo con el formato de salida JSON.
🔁 El hook Stop no deja parar a Claude
  • Claude Code anula un Stop hook tras 8 bloqueos seguidos. Comprueba stop_hook_active y sal pronto si es true:
stop-hook.sh
🔍 ¿Cómo sé qué hizo un hook?
  • Ctrl+O abre la vista de transcripción. Si todo va bien, no verás nada: comprueba el efecto (p. ej. el archivo formateado).
  • Log completo: claude --debug-file /tmp/claude.log y en otra terminal tail -f /tmp/claude.log. A mitad de sesión: /debug.
🚧 Límites a tener en cuenta
  • PostToolUse no puede deshacer: la herramienta ya se ejecutó.
  • Stop se dispara cada vez que Claude termina de responder, no sólo al acabar la tarea.
  • Timeout por defecto de command: 10 min (30 s en UserPromptSubmit). Cámbialo con timeout en segundos.
  • Un deny de PreToolUse bloquea incluso en modo bypassPermissions; pero un allow no salta las reglas de denegación de settings.
