Una rama no copia nada

Una rama es un puntero móvil a un commit. Crearla es escribir un archivo con un hash [1].

HEAD apunta a la rama en la que estás [1].

Cada git commit mueve hacia adelante solo esa rama [1].

Para crear una rama y cambiarte a ella: git switch -c feature (Git 2.23 o posterior) o git checkout -b feature [1].

Antes de tocar nada: estás en feature y main apunta al mismo commit. Haces git commit. ¿Qué etiqueta avanza?

  1. Una rama es solo un puntero móvil a un commit: crearla no copia nada.
  2. HEAD apunta a la rama en la que estás. Aquí estás en feature.
  3. Cada git commit crea un commit hijo del actual y mueve hacia adelante una sola etiqueta: la rama a la que apunta HEAD. ¿Cuál es?
  4. Solo feature. HEAD apunta a feature, así que solo esa etiqueta avanza al commit nuevo; main se queda donde estaba.

Estás en feature. main y feature apuntan al mismo commit.

  1. Antes de tocar un botón, mira la etiqueta ámbar: es la rama a la que apunta HEAD.
  2. git commit agrega un tramo después de esa etiqueta y la mueve a él. La otra etiqueta se queda donde estaba.
  3. git switch no mueve ningún commit: solo cambia a qué rama apunta HEAD.
  4. Para que las ramas diverjan, cada una necesita un commit que la otra no tenga. ¿Qué tienes que hacer entre un commit y el siguiente?
  5. Haz git commit en feature, luego git switch main y otro git commit. Cada rama avanzó por su lado desde el mismo commit, que ahora es su ancestro común: divergieron.
  • Haz que las ramas diverjan: al menos un commit en main y otro en feature que la otra no tenga.

git merge con ramas divergentes

Un tramo nuevo: ¿con qué lo arma Git?

Si las dos ramas avanzaron, Git crea un commit de fusión con más de un padre [2]. Para armarlo compara versiones del proyecto. ¿Cuáles?

  1. Git usa las dos puntas y su ancestro común [2].
  2. El ancestro común dice qué había antes. Comparando cada punta contra él, Git sabe qué cambió de cada lado.
  3. Si solo un lado cambió un renglón, gana ese cambio. Si los dos lo cambiaron distinto, hay conflicto.
  4. La estrategia por defecto se llama ort y resuelve dos puntas con un merge de tres vías [4].

Predice: ¿cuántas versiones del proyecto compara Git para armar el commit de fusión?

  1. Piensa en un solo renglón: para combinarlo, Git necesita saber si cambió y de qué lado.
  2. Con solo las dos puntas ve que el renglón es distinto, pero no cuál de los dos lo cambió. Le falta saber qué había antes.
  3. Lo que había antes está en el último commit que comparten las dos ramas: el ancestro común. Git compara cada punta contra él; los commits intermedios no le hacen falta. Cuenta cuántas versiones son.
  4. 3: las dos puntas y el ancestro común. Comparando cada punta contra el ancestro, Git sabe qué cambió cada lado; por eso se llama three-way merge.

Toca un tramo con borde (o usa Tab y Enter) para ver su papel.

  • Toca los tramos resaltados del dibujo y descubre qué papel tiene cada uno en la fusión.

Fast-forward o commit de fusión

Antes de fusionar, Git se fija en si hay trabajo divergente: si las dos ramas avanzaron desde que se separaron. ¿Qué cambia cuando solo avanzó una?

Predice: creaste hotfix desde main, hiciste un commit y main no se movió. Estando en main corres git merge hotfix. ¿Qué queda?

  1. Primero pregúntate si hay trabajo divergente: ¿main avanzó después de que creaste hotfix?
  2. No: main no se movió, así que el commit de hotfix desciende directamente de main.
  3. Si la rama que fusionas desciende de la tuya, no hay dos lados que combinar ni renglones que puedan chocar. ¿Hace falta un commit nuevo, o basta con mover algo?
  4. main avanza al commit de hotfix, sin commit nuevo. Es un fast-forward: como no hay divergencia, Git solo mueve el puntero de main hacia adelante.

Sin divergencia

Fast-forward

$ git merge hotfix
Updating f42c576..3a0874c
Fast-forward
 index.html | 2 ++
 1 file changed, 2 insertions(+)

Si la rama que fusionas desciende de la tuya, no hay trabajo divergente: Git solo mueve el puntero hacia adelante. La salida dice Fast-forward y no hay commit nuevo [2].

Las dos avanzaron

Commit de fusión

Git crea un snapshot nuevo con el resultado del three-way merge y un commit que apunta a él, con dos padres [2].

Cómo controlarlo [4]
--ffPor defecto. Fast-forward cuando se puede; si no, commit de fusión.
--no-ffSiempre crea un commit de fusión, aunque se pudiera hacer fast-forward.
--ff-onlySolo fast-forward. Si no se puede, se niega a fusionar y sale con error.

Merge contra rebase, con las mismas ramas

Merge y rebase llevan tu trabajo a la otra rama por caminos distintos. ¿Qué les pasa a tus commits en cada caso?

Un commit guarda el ID de su padre, y su ID es un hash de su contenido [7].

Rebase reaplica cada commit tuyo encima de la otra rama, en orden; merge toma las dos puntas y las une [3]. Como cada copia queda sobre otro padre, tiene otro hash: rebase abandona commits y crea otros parecidos pero distintos [3].

Antes de mover nada: feature tiene 3 commits y main avanzó 2 desde que se separaron. En feature corres git rebase main. ¿Cuántos commits con hash nuevo aparecen?

  1. Recuerda qué hace rebase: reaplica cada commit tuyo, en orden, encima de la otra rama. No junta nada en un solo commit.
  2. ¿Cuáles son tus commits? Los de feature desde que se separó de main. Los de main ya están en la base sobre la que reaplicas y no se tocan.
  3. Un commit guarda el ID de su padre, y su ID es un hash de su contenido. Si la copia tiene otro padre, ¿puede conservar el mismo hash?
  4. 3: una copia por commit de feature. Cada uno se reaplica sobre un padre distinto y recibe un hash nuevo; los 2 commits de main se quedan igual.

la regla de oro

        
No hagas rebase de commits que existen fuera de tu repositorio y sobre los que otros pudieron basar trabajo. [3]

        
Si lo haces, tu equipo tendrá que volver a fusionar su trabajo y el historial se enreda [3].

        
Lo que sí: rebase local antes de publicar para ordenar tu trabajo; lo que ya publicaste, nunca [3]. Para ordenar, git rebase -i cambia pick por reword, edit, squash, fixup o drop [5].

        
Si de verdad tienes que reescribir algo publicado, git push --force-with-lease solo sobrescribe si la rama remota sigue donde esperabas; si no, falla [10].

Git se detiene a mitad de la fusión

            
$ git merge feature
Auto-merging app.conf
CONFLICT (content): Merge conflict in app.conf
Automatic merge failed; fix conflicts and then commit the result.

            
No hay commit de fusión todavía [2]. HEAD no se movió y la ref MERGE_HEAD apunta a la punta de feature [4].

          

          

            
Resuelto

            
git status te dice qué falta

            
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   app.conf

            
Para cada archivo en conflicto, el índice guarda hasta tres versiones: stage 1 el ancestro común, stage 2 HEAD y stage 3 MERGE_HEAD. Las ves con git ls-files -u [4].

          

          

            
Tu turno

            
Lee los marcadores

            

              
En app.conf, ¿qué hay entre <<<<<<< HEAD y =======?

              

                
                
                
              

              

              

                
    
                  
  1. HEAD es la rama en la que estabas parado al correr git merge. Aquí estás en main y fusionas feature.
    2. 
                  
  2. Cada marcador nombra su lado: <<<<<<< HEAD abre el bloque de arriba, >>>>>>> feature cierra el de abajo y ======= los separa.
    3. 
                  
  3. El texto del ancestro común solo aparece con el estilo diff3, tras |||||||. Aquí no hay ese marcador.
    4. 
                  
  4. Lo de HEAD: tu rama actual, main (timeout = 45). Arriba del ======= va HEAD (ours) y abajo la rama que fusionas, feature (theirs).
    5. 
                

              

            

            
Arriba: timeout = 45, de main. Abajo: timeout = 60, de feature [2]. Borras los marcadores y dejas lo que debe quedar.

            
¿Por qué funciona? Piénsalo y luego ábrelo
HEAD es la rama en la que estás parado. Al fusionar, tu rama es "ours" (stage 2) y la que entra es "theirs" (stage 3); los marcadores siguen ese orden.

          

          

            
Tu turno

            
Marca el archivo como resuelto

            

              
Dejaste timeout = 60 sin marcadores y guardaste. ¿Qué le dice a Git que ese archivo ya está resuelto?

              

                
                
                
              

              

              

                
    
                  
  1. Recuerda dónde vive el conflicto: en el índice, que guarda tres stages del mismo archivo (base, HEAD y feature).
    2. 
                  
  2. Guardar el archivo cambia lo que tienes en disco, pero el índice sigue con sus tres stages: para Git el conflicto sigue ahí.
    3. 
                  
  3. Necesitas un comando que ponga en el índice una sola versión, la que dejaste. git merge --abort no sirve: tira toda la fusión.
    4. 
                  
  4. git add app.conf. Al agregar el archivo al staging, sus tres stages se reemplazan por tu versión y Git lo marca como resuelto.
    5. 
                

              

            

            
$ git add app.conf
$ git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

            
¿Por qué funciona? Piénsalo y luego ábrelo
El conflicto vive en el índice: tres stages del mismo archivo. git add los reemplaza por una sola versión, la tuya [2].

          

          

            
Tu turno

            
Sella la fusión

            

              
Ya no hay archivos sin resolver. ¿Qué comando crea el commit de fusión?

              

                
                
                
              

              

              

                
    
                  
  1. Pregúntate qué operación está en curso. git status lo dijo en el paso anterior: "you are still merging".
    2. 
                  
  2. El comando que cierra tiene que ser de esa operación. git rebase --continue es para un rebase en curso, y aquí no hay ninguno.
    3. 
                  
  3. git push manda tu rama al remoto; no crea commits, y el commit de fusión todavía no existe.
    4. 
                  
  4. git merge --continue (o git commit). Revisa que haya una fusión en curso y llama a git commit, que crea el commit con dos padres: el HEAD de antes y MERGE_HEAD.
    5. 
                

              

            

            
$ git merge --continue
[main e5b2c90] Merge branch 'feature'

            
Si en cualquier momento prefieres no fusionar, git merge --abort intenta volver al estado previo [4].

            
¿Por qué funciona? Piénsalo y luego ábrelo
Con todo resuelto en el índice, el commit toma ese snapshot y anota dos padres: el HEAD de antes y MERGE_HEAD [4].

          

          

            
Arma tú la secuencia

            
El mismo conflicto, pero en un rebase

            

              
Ahora estás en feature y corres git rebase main. Sale el mismo conflicto. ¿Qué secuencia lo resuelve?

              

                
                
                
              

              

              

                
    
                  
  1. Resolver el conflicto en sí no cambia: editas app.conf y lo marcas como resuelto con git add, igual que en el merge.
    2. 
                  
  2. Lo que cambia es la operación en curso: ahora es un rebase, no un merge.
    3. 
                  
  3. Cada operación sigue con su propio --continue: el merge con git merge --continue, y el rebase con…
    4. 
                  
  4. editar → git add app.conf → git rebase --continue. Rebase es una serie de fusiones pequeñas, una por commit reaplicado: cada una se resuelve igual y se sigue con el rebase, que puede volver a pararse en el siguiente commit.
    5. 
                

              

            

            
$ git rebase main
CONFLICT (content): Merge conflict in app.conf
# editas app.conf
$ git add app.conf
$ git rebase --continue

            
Rebase se detiene en el primer commit problemático. Además de --continue tienes git rebase --skip (salta ese commit) y git rebase --abort (vuelve a la rama original) [5].

            
¿Por qué funciona? Piénsalo y luego ábrelo
Rebase es una serie de pequeñas fusiones, una por commit reaplicado. Cada una se resuelve igual: editar, git add y seguir con la operación que está en curso, que aquí es el rebase.

ours, theirs y las salidas de emergencia

    
--ours y --theirs señalan stages del índice, no ramas [6]. ¿Señalan el mismo lado en un merge que en un rebase?

    

      

        
Probador: ¿qué versión te queda?

        
Estás en feature, donde pusiste timeout = 60. En main pusieron timeout = 45 y además agregaron log = info, que no choca con nada.

        

          
Predice: corres git rebase main y hay conflicto en app.conf. Quieres quedarte con TU versión. ¿Qué escribes?

          

            
            
          

          

          

            
    
              
  1. --ours y --theirs señalan stages del índice, no ramas: ours es el stage 2 y theirs el stage 3.
    2. 
              
  2. Piensa qué hace rebase: parte de la punta de main y reaplica encima tus commits, uno por uno.
    3. 
              
  3. El punto de partida, la rama sobre la que reaplicas, ocupa el lugar de ours. Tu trabajo es lo que va entrando. ¿Qué lado es entonces tu versión?
    4. 
              
  4. git checkout --theirs app.conf. Durante un rebase los lados se ven intercambiados: --ours es main, la rama sobre la que reaplicas, y --theirs es tu commit que se está reaplicando.

Ver la base

        
Con el estilo diff3, el conflicto muestra también el texto original tras ||||||| [4].

        
<<<<<<< HEAD
timeout = 45
||||||| base
timeout = 30
=======
timeout = 60
>>>>>>> feature

        
git config --global merge.conflictStyle zdiff3 hace lo mismo y quita los renglones iguales de las orillas del conflicto [4]. zdiff3 existe desde Git 2.35 [11].

      

      

        
Que Git recuerde

        
rerere (reuse recorded resolution) guarda cómo resolviste un conflicto y lo reaplica cuando vuelve a salir el mismo, por ejemplo al rebasar una rama larga varias veces [8].

        
$ git config --global rerere.enabled true

      

      

        
Volver atrás

        
git merge --abort y git rebase --abort cancelan la operación a medias [4] [5]. Al empezar, rebase deja ORIG_HEAD en la punta vieja [5].

        
Si ya terminaste, git reflog guarda dónde estuvo cada rama: HEAD@{2} es donde estaba HEAD dos movimientos atrás. Las entradas duran 90 días, o 30 si ya no son alcanzables [9].

      

      

        
Antes de fusionar, deja limpio el árbol

        
Si había cambios sin commit al empezar, git merge --abort a veces no puede reconstruirlos. Haz commit o git stash antes de git merge [4].
