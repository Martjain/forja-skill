Cómo funciona git

Git guarda tu proyecto como un hilo de fotos. Cada foto es un commit, y cada rama es una etiqueta que cuelga de una de ellas y avanza cuando el hilo crece.

02 · La pieza básica

commit

una foto de todos tus archivos, con un nombre que nadie más tiene

Un commit es una foto de todo tu proyecto

Cada vez que haces commit, git toma una foto de cómo están todos tus archivos en ese momento y la guarda [1].

Git nació en 2005. La comunidad del kernel de Linux, con Linus Torvalds, perdió el uso gratuito de BitKeeper y armó su propia herramienta: rápida, simple y totalmente distribuida [4].

Tienes la historia completa en tu disco. Por eso casi todo funciona sin red y se siente instantáneo [1].

Antes de leer la ficha: ¿cuántos padres tiene el primer commit de un repositorio?

  1. Mira la ficha: el padre de un commit es el commit anterior, el que vino justo antes.
  2. Piensa en el primer commit del repositorio: antes de él, ¿hay algún commit guardado en .git?
  3. El padre tiene que ser otro commit que ya exista: no puede ser el mismo commit ni una carpeta.
  4. Ninguno. El primer commit no tiene un commit anterior al que apuntar, así que tiene cero padres. Uno normal tiene uno y uno de fusión, dos o más.

Qué guarda un commit [2]

hash
463dc4f, los primeros 7 de sus 40 caracteres
foto
un puntero a la foto de lo que pusiste en el staging area
autor
tu nombre y tu correo
mensaje
lo que escribiste en -m "…"
padres
el commit anterior. El primero tiene cero; uno normal, uno; uno de fusión, dos o más.

Antes del primer commit, dile a git quién eres. Ese nombre y ese correo quedan grabados en cada commit que crees [5]:

$ git config --global user.name "Tu Nombre"
$ git config --global user.email tu@correo.com

03 · Dónde vive cada versión

Tres zonas: tu carpeta, la mesa de armado y el archivo

Un cambio viaja de tu carpeta al staging area con git add, y de ahí al repositorio con git commit.

Git las llama working tree, staging area (su nombre técnico es index) y directorio .git [1].

Toca cada caja y cada flecha del diagrama. La ficha te dice qué hay ahí.

  • Abre la ficha de las tres zonas
  • Encuentra el comando que trae una foto guardada de vuelta a tu carpeta

Antes de tocar nada: alguien hace git clone de tu proyecto en su máquina. ¿Qué zona se copia?

  1. Repasa las tres zonas: el working tree es tu carpeta, el staging area es lo que preparas para el próximo commit y .git es el repositorio.
  2. ¿En cuál de las tres están todos los commits, la historia completa?
  3. Lo que tienes a medio editar en tu carpeta o a medio preparar en el staging area es local: todavía no es parte de la historia.
  4. El directorio .git. Ahí están los metadatos y la base de objetos con todos los commits. Es lo que se copia al clonar; de ahí git saca después los archivos de la carpeta de la otra persona.

EditasCambias README.md en tu carpeta. Solo cambió el working tree.

Al clonar se copia el directorio .git: la parte más importante, con todos los commits [1]. Tu working tree y tu staging area son locales: los de la otra persona se arman desde esa copia.

04 · Laboratorio

Mesa de trabajo: ¿qué se lleva el commit si editas después de git add?

Entre git add y git commit puedes seguir editando el archivo. Prueba en la mesa cuál de las versiones termina en el commit.

Antes de tocar la mesa: editas README.md (v2), haces git add, lo vuelves a editar (v3) y haces git commit. ¿Qué versión de README.md queda en el commit?

  1. Ordena lo que pasa: editas (v2), git add, editas otra vez (v3), git commit.
  2. git add copia el archivo al staging area tal como está en ese instante. ¿Qué versión había cuando lo hiciste?
  3. Después editas a la v3 en tu carpeta, pero no vuelves a hacer git add. ¿Cambió algo en el staging area?
  4. git commit guarda lo que hay en el staging area, no lo que hay en tu carpeta.
  5. La v2. Es la que estaba en el staging area al hacer commit. La v3 se queda en tu carpeta y git status -s te avisa con M README.md hasta que vuelvas a hacer git add.

            05 · Cómo guarda
            
      
            Si cambias un archivo, ¿cuánto guarda git?
            
      
            La mayoría de los otros sistemas guardan qué cambió en cada archivo. Git guarda en cada commit una foto de todo el proyecto. ¿Quiere decir eso que copia todo cada vez?
            
    
            
    
            
      
            
        
            Antes de mover el slider: tu proyecto tiene 8 archivos y cambias solo 1. En el commit nuevo, ¿cuántos archivos guarda git de nuevo?
            
        
            
          
          
          
        
            
        
            
        
            
          
              
            
            1. Recuerda la idea de la sección: en cada commit git guarda una foto completa de tu proyecto.
              2. 
            
            2. Una foto completa no obliga a copiarlo todo: lo que no cambió, git lo enlaza a la copia que ya tenía.
              3. 
            
            3. Cuenta: de los 8 archivos, ¿cuántos cambiaron y cuántos quedaron idénticos al commit anterior?
              4. 
            
            4. Guardar solo las líneas cambiadas es lo que hacen los otros sistemas, con su lista de cambios. Git no trabaja así.
              5. 
            
            5. Solo 1; los otros 7 son enlaces. El archivo que cambió se guarda como copia nueva y los 7 iguales apuntan a las copias que ya existían. Aun así, el commit es una foto completa de los 8.

            06 · Paso a paso
            
      
            Ramas: etiquetas que avanzan solas
            
      
            Una rama es una etiqueta que apunta a un commit. HEAD marca en cuál estás, y esa etiqueta avanza con cada commit nuevo [2].
            
    
            
    
            
      
              
        
              2. 
        
              3. 
        
              4. 
        
              5. 
        
              6. 
        
              7. 
      
            
      
            Paso 1 de 6
            
      
            
        
            
          
        
            
        
            
          
            
            
            1. Tres commits en main
            

            $ git commit -m "A"
$ git commit -m "B"
$ git commit -m "C"
            
            
            Cada commit apunta a su padre: C a B, B a A. La etiqueta main apunta al último, y HEAD apunta a main. Así sabe git en qué rama estás [2].
            
            
            git init llama master a la rama inicial, salvo que configures init.defaultBranch; pasará a ser main cuando salga Git 3.0 [6]. Muchos servicios de alojamiento de repositorios ya crean la rama inicial como main, así que aquí usamos main.
            
          
            
          
            
            
            2. Crear la rama idea
            

            $ git branch idea
            
            
            Aparece una etiqueta nueva, idea, en el mismo commit donde estás (C). Fíjate en HEAD: no se movió. git branch solo crea la etiqueta; no te cambia a ella [2].
            
            
            No se copió ningún archivo. Crear una rama es escribir un archivo de 41 bytes.
            
          
            
          
            
            
            3. Empezar a trabajar en idea
            
            
            
              
            Tu turno: quieres que tus próximos commits vayan a idea. ¿Qué escribes?
            
              
            
                
                
                
              
            
              
            
              
            
                
              
                  
            1. Repasa el paso 2: git branch idea creó la etiqueta, pero HEAD no se movió.
              2. 
                  
            2. Los commits nuevos van a la rama a la que apunta HEAD. Necesitas un comando que mueva HEAD a idea.
              3. 
                  
            3. Descarta: git branch idea ya lo hiciste y solo crea la etiqueta; git commit guarda una foto, no te cambia de rama.
              4. 
                  
            4. git switch idea. Mueve HEAD a idea y deja tu carpeta y el index como están en esa rama; desde ahí, tus commits se agregan en su punta.
              5. 
                
            
              
            
            
            

            $ git switch idea
Switched to branch 'idea'
            
            
            ¿Por qué funciona? Piénsalo y luego ábrelo
              
            git switch cambia de rama: el working tree y el index se actualizan para coincidir con ella, y los commits nuevos se agregan en su punta [7]. Como idea y main apuntan a C, tus archivos no cambian; solo se mueve HEAD. git checkout idea hace lo mismo y lo verás en muchos tutoriales [2]. Atajo: git switch -c idea crea la rama y te cambia en un solo paso [7].
            
            
            
          
            
          
            
            
            4. Un commit en idea
            

            $ git commit -m "D"
            
            
            
              
            Tu turno: estás en idea y haces el commit D. ¿Qué etiqueta avanza?
            
              
            
                
                
                
              
            
              
            
              
            
                
              
                  
            1. Después del paso 3, ¿a qué rama apunta HEAD?
              2. 
                  
            2. La regla de la sección: la etiqueta a la que apunta HEAD avanza con cada commit nuevo.
              3. 
                  
            3. ¿Hay alguna regla que mueva las etiquetas a las que HEAD no apunta?
              4. 
                  
            4. idea. HEAD apunta a idea, así que idea pasa a D. main se queda en C, esperando.
              5. 
                
            
              
            
            
            
            
            idea pasa a D. main sigue en C.
            
            
            ¿Por qué funciona? Piénsalo y luego ábrelo
              
            HEAD apunta a la rama en la que estás, y git mueve esa rama hacia el commit nuevo. Las demás etiquetas no se tocan [2]. Por eso puedes probar algo en idea sin que main se entere.
            
            
            
          
            
          
            
            
            5. Volver a main y hacer otro commit
            

            $ git switch main
$ git commit -m "E"
            
            
            
              
            Tu turno: ¿cómo queda el hilo después del commit E?
            
              
            
                
                
                
              
            
              
            
              
            
                
              
                  
            1. Al hacer git switch main, HEAD vuelve a main. ¿A qué commit apunta main? (En el paso 4 se quedó en C.)
              2. 
                  
            2. Al cambiar de rama, git regresa tus archivos a la foto a la que apunta esa rama. ¿Está D en esa foto?
              3. 
                  
            3. Un commit nuevo toma como padre el commit donde estás. ¿Cuál es el padre de E?
              4. 
                  
            4. idea sigue apuntando a D, que también salió de C. ¿Cuántos commits salen ahora de C?
              5. 
                  
            5. Se abre en dos: E sale de C. E toma C como padre, igual que D, así que quedan dos caminos: C → D (idea) y C → E (main). La historia divergió.
              6. 
                
            
              
            
            
            
            
            E sale de C. Ahora hay dos caminos: C → D (idea) y C → E (main). La historia divergió.
            
            
            ¿Por qué funciona? Piénsalo y luego ábrelo
              
            Al cambiar a main, HEAD vuelve a main y git regresa tus archivos a la foto a la que apunta main [2]. D no está en esa foto. Cada rama guarda su trabajo aislado, y puedes ir y venir entre ellas.
            
            
            
          
            
          
            
            
            6. Juntar idea con main
            
            
            
              
            Ármalo tú: estás en main (paso 5) y quieres traer D. ¿Qué comando lo une?
            
              
            
                
                
                
              
            
              
            
              
            
                
              
                  
            1. ¿Qué quieres? Traer el trabajo de idea (D) a la rama en la que estás, main.
              2. 
                  
            2. Descarta lo que ya conoces: git switch te cambia de rama, no une nada; git add pone archivos en el staging area.
              3. 
                  
            3. Como las dos ramas avanzaron desde C, git tiene que crear un commit de fusión, con dos padres: E y D. ¿Qué comando fusiona otra rama en la tuya?
              4. 
                  
            4. git merge idea. Estando en main, trae el trabajo de idea; como las ramas divergieron, git crea el commit de fusión F con dos padres, E y D.
              5. 
                
            
              
            
            
            

            $ git merge idea
# commit de fusión F, con dos padres: E y D
            
            
            ¿Por qué funciona? Piénsalo y luego ábrelo
              
            Como las ramas divergieron, git hace una fusión de tres vías: compara las dos puntas (E y D) con su ancestro común (C) y crea un commit de fusión, que tiene más de un padre [8].
            
              
            Si main no hubiera avanzado, no haría falta: git solo movería la etiqueta hacia adelante. Eso se llama fast-forward [8].
            
              
            Si las dos ramas cambiaron la misma parte del mismo archivo, git se detiene con CONFLICT y marca el archivo con <<<<<<<, ======= y >>>>>>>. Lo arreglas a mano y haces git add para marcarlo como resuelto [8].
            
            
            
          
            
          
            
            
            
          
            
          
              
            
            • Llega al commit de fusión F

            07 · La regla que no se olvida
            
      
            Una rama no es una copia de tu proyecto. Es un papelito con el hash de un commit.
            
      
      
            Por dentro, una rama es un archivo que contiene los 40 caracteres del hash del commit al que apunta. Crearla es escribir 41 bytes, y por eso crear y borrar ramas es barato [2].
            
      
            Para nombrar un commit no necesitas los 40: bastan los primeros, si son al menos 4 y ningún otro objeto empieza igual. git log --abbrev-commit muestra 7 [9].
            
    
            
  
            

  
  
            
    
            
      
            08 · Trabajar con otros
            
      
            Remotos: la misma historia en otra máquina
            
      
            Un remoto es otra copia de tu repositorio en la red. git push sube tus commits; git fetch y git pull traen los de los demás [10].
            
    
            
    
            
      
      
            
        
            git clone <url>
            
        
            Baja todos los datos, llama origin al servidor y te da tu propia rama local, que empieza donde está la del servidor [11].
            
      
            
      
            
        
            fetch o pull
            
        
            git fetch solo descarga: no toca tu trabajo. git pull descarga y trata de fusionar en tu rama actual [10].
            
      
            
      
            
        
            git push origin main
            
        
            
          
            Predice: tú y tu compañera clonaron al mismo tiempo. Ella hizo push primero. ¿Qué pasa con tu git push?
            
          
            
            
            
            
          
            
          
            
          
            
            
              
              
            1. Ella hizo push primero: ahora origin tiene un commit que tú no tienes.
              2. 
              
            2. La fusión no la hace el servidor: git pull descarga y trata de fusionar en tu rama actual, en tu máquina.
              3. 
              
            3. Entonces, antes de subir, ¿qué tiene que tener tu rama que hoy no tiene?
              4. 
              
            4. Git lo rechaza: primero trae lo de ella. El push solo funciona si nadie subió algo en el medio. Trae su trabajo con git pull (o git fetch), incorpóralo y vuelve a subir.
              5. 
            
            
          
            
        
            
        
            

            $ git push origin main
# rechazado: origin tiene un commit que tú no tienes
$ git pull
# trae su commit y lo fusiona con el tuyo
$ git push origin main
# ahora sí sube
            
          
            El push solo funciona si nadie subió algo en el medio. Si alguien lo hizo, primero trae su trabajo e incorpóralo [10].
