Hooks de Claude Code: estaciones fijas en tu sesión

Tu sesión es una banda que avanza. Un hook es una estación atornillada en un punto de la banda: cada vez que pasa una pieza por ahí, tu comando corre. Siempre, sin que Claude tenga que acordarse.[1]

  • 30+eventos donde puedes atornillar una estación[2]
  • 2el código de salida que detiene la pieza[2]
  • 600 stimeout por defecto de un hook command[1]

SessionStartEmpieza la sesión y corre tu hook de SessionStart, una sola vez.

Estación 02

Pedirlo o garantizarlo

Una instrucción le pide algo a Claude; un hook lo hace pasar siempre, en el mismo punto.

Instrucción el modelo decide

Escribes en CLAUDE.md o en el prompt "después de editar, corre prettier". Claude lo lee y decide si lo hace en cada momento.

Hook Claude Code lo ejecuta

Es un comando de shell que tú defines. Claude Code lo corre en un punto exacto de su ciclo de vida, así que la acción siempre pasa, en lugar de depender de que el modelo elija hacerla.[1]

Antes de seguir: pones en CLAUDE.md la línea "corre prettier después de cada edición". ¿Qué te garantiza eso?

  1. Piensa en quién lee CLAUDE.md: es texto que Claude recibe como contexto, igual que un prompt.
  2. Con una instrucción, el modelo decide en cada momento si la sigue. Es el lado izquierdo de la figura: un cruce con un signo de pregunta.
  3. Para que algo pase siempre, tiene que ejecutarlo Claude Code mismo en un punto fijo de su ciclo de vida, sin preguntarle al modelo. ¿Una línea de texto hace eso?
  4. Bloquear una edición tampoco lo hace un archivo de instrucciones: eso le toca a un hook.
  5. Nada: Claude lo hará cuando lo decida. CLAUDE.md es contexto que el modelo lee y decide si sigue; para garantizarlo necesitas un hook, que Claude Code ejecuta siempre.

Para garantizarlo, la estación correcta es PostToolUse con el matcher Edit|Write: corre después de cada edición de archivo, sin excepción.[1] En la sección 04 vas a ver cómo se escribe.

Estación 03

Las estaciones de la sesión

Cada evento es un punto fijo de la banda. Unos pasan una vez por sesión, otros una vez por turno y otros en cada herramienta.[2]

La referencia oficial tiene más de 30 eventos. Estos 8 cubren lo básico. Toca una estación para ver su ficha.

Antes de tocar: quieres impedir que Claude edite tu .env. ¿En qué estación pones el hook?

  1. ¿Qué te piden? Impedir la edición: el hook tiene que actuar antes de que el archivo cambie.
  2. Busca en la banda las estaciones que pasan en cada herramienta (las naranjas). Una corre antes de la llamada y otra después de que termina.
  3. Si el hook corre cuando la herramienta ya terminó, el .env ya cambió: llega tarde. Stop corre cuando Claude termina de responder, todavía más tarde.
  4. Necesitas la estación que llega a tiempo y que, con exit 2, puede cancelar la llamada.
  5. PreToolUse. Corre antes de que se ejecute la herramienta y puede bloquearla; PostToolUse llega cuando el archivo ya cambió.

Desliza la banda hacia los lados para ver todas las estaciones.

  • una vez por sesión
  • una vez por turno
  • en cada herramienta
  • cuando hace falta

Retos

  • Encuentra la estación que llega tarde para impedir nada, porque la herramienta ya corrió
  • Encuentra las dos estaciones de turno, que no aceptan matcher

Estación 04

Anatomía de un hook

Tres niveles: el evento, un grupo con su matcher y el comando que corre.

  1. 1
    Evento. Una llave dentro del único objeto "hooks". Si ya tienes otros, agrega el nuevo como hermano, no reemplaces el objeto.[1]
  2. 2
    Grupo con matcher. Filtra cuándo dispara. En eventos de herramienta, filtra por nombre de herramienta.
  3. 3
    Handler. "type": "command" corre un comando de shell. Existen otros tipos (http, mcp_tool, prompt, agent), pero casi todos los hooks usan command.[1]

Tu comando recibe los datos del evento como JSON por stdin: el nombre del evento, la herramienta y sus argumentos.[1] Por eso los ejemplos oficiales empiezan con jq.

.claude/settings.jsonejemplo oficial

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

lo que llega por stdin a un hook PreToolUse[2]

{
  "session_id": "abc123",
  "cwd": "/home/user/my-project",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "npm test" }
}

Cada handler puede llevar "timeout" en segundos. Sin él, un command tiene 10 minutos.[1] No sabes JSON de memoria: también puedes pedirle a Claude que escriba el hook por ti.[1]

Estación 05

El matcher: el lector de etiquetas

La estación lee la etiqueta de cada pieza y solo dispara con las que coinciden.

Tres reglas, según los caracteres que escribas: "*", "" o sin matcher disparan con todo. Solo letras, dígitos, _, -, espacios, , y | es una lista exacta. Cualquier otro carácter lo convierte en expresión regular de JavaScript, sin anclar.[2] Y distingue mayúsculas.[1]

Antes de probar: escribes Edit.* como matcher de PreToolUse. ¿Con qué herramientas dispara?

  1. Primero el modo: revisa los caracteres de Edit.*. ¿Son todos letras, dígitos, _, -, espacios, , o |?
  2. El . y el * no están en esa lista, así que el matcher es una expresión regular de JavaScript.
  3. La regex no está anclada: basta con que el patrón aparezca en cualquier parte del nombre. Edit.* es «Edit seguido de cualquier cosa, o de nada».
  4. Recorre las herramientas y busca cuáles contienen el texto Edit, con E mayúscula. ¿Write lo contiene?
  5. Con Edit y NotebookEdit. Como regex sin anclar, Edit.* coincide con todo nombre que contenga «Edit»; para solo Edit usa ^Edit$ o simplemente Edit.
Prueba:

    Las herramientas de MCP se llaman mcp__<servidor>__<herramienta>, así que mcp__memory__.* atrapa todas las del servidor memory.[2]

    Retos

    • Escribe un matcher que dispare solo con Edit y Write, sin NotebookEdit
    • Atrapa las dos herramientas del servidor memory y nada más
    • Escribe el nombre de una herramienta en minúsculas y comprueba que no dispara
    1. Mira primero los caracteres del matcher: ellos deciden el modo. "*", "" o no poner matcher disparan con todo.
    2. Si solo usa letras, dígitos, _, -, espacios, , y |, es una lista exacta: cada nombre tiene que ser idéntico al de la herramienta.
    3. Cualquier otro carácter, como ., ^ o $, lo vuelve expresión regular de JavaScript sin anclar: basta con que el patrón aparezca en cualquier parte del nombre. Usa ^…$ para exigir el nombre completo.
    4. En los dos modos se distinguen mayúsculas: bash no es Bash.
    5. Las herramientas de MCP se llaman mcp__<servidor>__<herramienta>: el prefijo de un servidor sirve para atrapar todas las suyas.
    6. Para los retos: Edit|Write (lista exacta, deja fuera a NotebookEdit), mcp__memory__.* (regex con el prefijo del servidor) y un nombre en minúsculas como bash, que no dispara con nada.

    Estación 06

    El código de salida decide

    Tu script le contesta a Claude Code con su código de salida: 0 es "sin objeción", 2 es "detén esto".

    2

    exit 2 es el único código que bloquea. El mensaje que acompaña al bloqueo es tu stderr.[2]

    Antes de mover nada: tu hook de PreToolUse detecta un rm -rf y termina con exit 1. ¿Qué pasa?

    1. Lo que decide es el código de salida: es la respuesta de tu script a Claude Code.
    2. De los tres códigos de esta estación, solo uno bloquea. ¿Cuál es? ¿Es el 1?
    3. En Unix, 1 es el código de error de siempre. Para Claude Code, un 1 (o cualquier código que no sea 0 ni 2) significa que tu hook falló, no que objeta.
    4. Un fallo del hook no es una orden de detenerse. Piensa si eso frena el comando o solo queda registrado.
    5. El comando corre igual y aparece un aviso. exit 1 es un error que no bloquea: el rm -rf sigue y el transcript muestra «hook error». Para hacer cumplir la regla, usa exit 2 con un mensaje en stderr.
    Session StartPromptPrePostNotif.Stop
    exit 0exit 1 (u otro)exit 2
    sigue con aviso

    Retos

    • Bloquea un prompt antes de que llegue a Claude
    • Encuentra dónde exit 2 avisa a Claude pero ya no puede deshacer nada
    • Haz que Claude siga trabajando en lugar de detenerse

    Regla práctica para empezar: exit 0 cuando todo está bien, exit 2 con un mensaje en stderr cuando quieres detener algo. Evita exit 1 para hacer cumplir reglas.[2]

    Estación 07

    Tu primer hook: proteger .env

    Arma, paso a paso, el ejemplo oficial que impide editar archivos sensibles.[1]

    Paso 1 de 6flechas ← → para moverte

    Resuelto

    Lee lo que Claude Code te manda

    Crea el script. Lo primero es leer el JSON que llega por stdin y sacar la ruta del archivo que Claude quiere editar.

    .claude/hooks/protect-files.sh

    #!/bin/bashINPUT=$(cat)FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

    cat lee todo stdin. // empty devuelve vacío si el campo no existe, en lugar de la palabra null.

    Compara contra la lista de protegidos

    Una lista de patrones y un ciclo que revisa si la ruta contiene alguno.

    .claude/hooks/protect-files.sh

    INPUT=$(cat)FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/")for pattern in "${PROTECTED_PATTERNS[@]}"; do  if [[ "$FILE_PATH" == *"$pattern"* ]]; then    # ¿qué va aquí? (paso 3)

    Las variables van entre comillas ("$FILE_PATH"): es una de las prácticas de seguridad oficiales.[2]

    Detén la pieza

    Tu turno: la ruta coincide con .env. ¿Qué escribes dentro del if?

    1. ¿Qué tiene que lograr esta línea? Dos cosas: detener la edición del .env y que Claude entienda por qué.
    2. Para detener: en la estación 06 viste que exit 0 es «sin objeción» y exit 1 es un error que no bloquea. ¿Qué código sí bloquea?
    3. Para que Claude entienda: cuando el hook bloquea, Claude lee el mensaje de tu stderr.
    4. En bash, echo "…" escribe en stdout; agregarle >&2 lo manda a stderr.
    5. echo "Blocked" >&2 ; exit 2. En PreToolUse, exit 2 cancela la herramienta, y el mensaje en stderr es lo que Claude lee para cambiar de plan.
      if [[ "$FILE_PATH" == *"$pattern"* ]]; then    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2    exit 2  fidoneexit 0  # ningún patrón coincidió: sin objeción
    ¿Por qué funciona? Piénsalo y luego ábrelo

    >&2 manda el texto a stderr, que es justo lo que Claude lee cuando el hook bloquea: así entiende por qué y cambia de plan. El exit 0 final deja pasar todo lo demás.

    Hazlo ejecutable

    Tu turno: guardaste el script en macOS o Linux. ¿Qué falta para que Claude Code pueda correrlo?

    1. El hook es un programa más: Claude Code lo lanza como se lanza cualquier script desde la terminal.
    2. En macOS y Linux, un archivo recién guardado no se puede ejecutar hasta que el sistema lo permita.
    3. ¿Y sudo? El hook ya corre con todos tus permisos de usuario (estación 09). Darle más permisos a Claude Code no hace ejecutable al archivo.
    4. Piensa qué cambia los permisos del archivo, no los del usuario.
    5. Darle permiso de ejecución, con chmod +x .claude/hooks/protect-files.sh. En macOS y Linux, Claude Code solo puede correr scripts de hook ejecutables; es lo primero que se revisa si un hook no corre.

    terminal

    $ chmod +x .claude/hooks/protect-files.sh
    ¿Por qué funciona? Piénsalo y luego ábrelo

    El hook es un programa más: si el sistema no lo deja ejecutar, Claude Code no puede lanzarlo. Si un script "no corre nunca", esto es lo primero que se revisa.[1] Y nada de sudo: el hook ya corre con todos tus permisos.

    Atorníllalo en la banda

    Tu turno: en .claude/settings.json, ¿qué evento y qué matcher usas?

    1. Son dos decisiones: el evento (cuándo corre) y el matcher (con qué herramientas).
    2. El evento: tienes que actuar antes de que el .env cambie. En la estación 03, ¿qué estación llega a tiempo y cuál llega tarde?
    3. El matcher: las herramientas que editan archivos se llaman Edit y Write. Con solo letras y |, el matcher es una lista exacta.
    4. Una lista exacta distingue mayúsculas: compara edit con el nombre real de la herramienta.
    5. PreToolUse + "Edit|Write". Pre corre antes de la edición y puede bloquearla; con Post el .env ya habría cambiado, y edit|write en minúsculas no coincide con ninguna herramienta.

    .claude/settings.json

    {  "hooks": {    "PreToolUse": [      { "matcher": "Edit|Write",        "hooks": [ { "type": "command",          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" } ] }    ]  }}
    ¿Por qué funciona? Piénsalo y luego ábrelo

    Pre llega a tiempo; Post llega tarde. Y el matcher distingue mayúsculas: edit no es Edit. $CLAUDE_PROJECT_DIR da una ruta absoluta al script, sin importar en qué carpeta esté Claude. Ojo: Claude también puede escribir archivos con Bash; si necesitas cubrir todo, la guía oficial sugiere revisar también Bash.[1]

    Pruébalo

    Junta todo: le pides a Claude "agrega un comentario a .env". ¿Qué pasa?

    1. Sigue la pieza por la banda: Claude intenta usar Edit sobre .env. ¿En qué estación está tu hook y deja pasar Edit su matcher Edit|Write?
    2. El script lee la ruta por stdin y la compara con la lista: .env coincide con un patrón protegido.
    3. Dentro del if, el script escribe en stderr y sale con exit 2. Recuerda qué hace exit 2 en PreToolUse.
    4. Descarta lo que contradiga el orden: si el hook corre antes de la herramienta, ¿puede haber una edición que revertir?
    5. Se bloquea antes de editar y Claude recibe el mensaje Blocked:. El hook corre en PreToolUse, coincide con .env, escribe en stderr y sale con 2: la edición se cancela antes de correr y Claude lee el motivo.

    Las cuatro piezas trabajan juntas: el script lee stdin, decide con exit 2, el sistema lo puede ejecutar y la configuración lo pone antes de cada edición. Escribe /hooks en Claude Code para confirmar que aparece bajo PreToolUse.[1]

    Estación 08

    Dónde vive un hook

    El archivo donde lo escribes decide a quién le aplica.

    Tres archivos de settings

    ~/.claude/settings.jsonTodos tus proyectos. Solo en tu máquina.
    .claude/settings.jsonUn proyecto. Se puede commitear y compartir con el equipo.
    .claude/settings.local.jsonUn proyecto, solo para ti. Queda en gitignore cuando Claude Code guarda ahí un ajuste.

    Los hooks de distintos niveles se suman; uno no reemplaza al otro.[2]

    /hooks

    Escríbelo en Claude Code para ver todos los hooks configurados, agrupados por evento.[1]

    Más lugares

    Settings administrados por tu organización, el hooks/hooks.json de un plugin y el frontmatter de una skill o un subagente.[1]

    Apagarlos y recargarlos

    "disableAllHooks": true en un archivo de settings los apaga; los de settings administrados siguen corriendo salvo que se apaguen ahí. Si editas el archivo con Claude Code abierto, normalmente detecta el cambio solo.[1]

    Estación 09

    Un hook de comando corre con todos tus permisos de usuario.

    Puede modificar, borrar o leer cualquier archivo al que tu cuenta tenga acceso. Revisa y prueba cada comando antes de agregarlo.[2]

    1. Valida la entrada: no confíes a ciegas en el JSON que llega.
    2. Pon comillas a las variables: "$VAR", no $VAR.
    3. Usa rutas absolutas para tus scripts, como "$CLAUDE_PROJECT_DIR".
    4. Evita tocar archivos sensibles: .env, .git/, llaves.[2]
    5. Con claude -p no aparece el diálogo de confianza: revisa la carpeta .claude/ de un repositorio ajeno antes de correrlo ahí.[2]
