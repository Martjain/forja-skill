Hooks: un comando que corre solo, en el momento exacto.

Un hook es un comando de shell que tú defines y que Claude Code ejecuta en puntos fijos de su ciclo de vida: antes de usar una herramienta, después de editar un archivo, cuando necesita tu atención.[1]

3piezas: evento, matcher y comando
exit 2bloquea la acción en los eventos que pueden bloquear[2]
600 stiempo límite por defecto de un hook command[2]

La idea central

Siempre.

Un hook no depende de que el modelo se acuerde. Si ocurre el evento, el comando corre.

La documentación lo llama control determinista: ciertas acciones pasan siempre, en lugar de depender de que el modelo decida hacerlas.[1]

Compara dos formas de pedir lo mismo, "formatea cada archivo que edites":

Si la decisión necesita criterio, y no una regla fija, existen hooks de tipo prompt o agent que consultan a un modelo de Claude. Para empezar, basta con el tipo command.[1]

Anatomía

Tu primer hook, línea por línea

Vas a crear el mismo hook con el que empieza la guía oficial: una notificación de escritorio cuando Claude Code espera tu respuesta.[1]

Fíjate en el anidado. Siempre es igual: hooks → evento → grupo con matcher → lista de handlers.

El ejemplo usa notify-send de Linux. En macOS la guía usa osascript y en Windows, PowerShell.[1]

Paso 1 de 6

{  "hooks": {    "Notification": [      {        "matcher": "",        "hooks": [          {            "type": "command",            "command": "notify-send 'Claude Code' 'Claude Code necesita tu atención'"          }        ]      }    ]  }}

Filtrar

¿A qué herramientas responde tu matcher?

Sin matcher, el hook corre en cada ocurrencia de su evento. En PreToolUse y PostToolUse, el matcher compara contra el nombre de la herramienta.[1]

Las reglas: "*", "" o sin matcher, todo. Si solo tiene letras, números, _, -, espacios, , o |, es una lista de nombres exactos. Cualquier otra cosa es una expresión regular de JavaScript sin anclar. Y distingue mayúsculas.[2]

"matcher": ""

    Responder

    exit 0 o exit 2: qué le dice tu script a Claude Code

    El hook recibe los datos del evento como JSON por stdin y responde con su código de salida.[1]

    exit 0

    Éxito, sin objeción. La acción sigue. En PreToolUse no aprueba la herramienta: sigue el flujo normal de permisos.[1]

    exit 2

    Error bloqueante. Lo que escribas en stderr es el motivo. Solo detiene la acción en eventos que pueden bloquear; en otros solo muestra el mensaje.[2]

    Dónde vive

    El archivo decide el alcance

    Un hook se escribe en un archivo de settings. Según cuál elijas, aplica a todos tus proyectos, a uno solo o a todo tu equipo. Los hooks de varios niveles se suman, no se reemplazan.[1]

    ~/.claude/settings.json

    Todos tus proyectos. Se queda en tu máquina. Buen lugar para la notificación de escritorio.

    globalsolo tú
    .claude/settings.json

    Un proyecto. Se puede commitear al repo y lo recibe todo el equipo.

    proyectocompartido
    .claude/settings.local.json

    Un proyecto, solo para ti. Queda en .gitignore cuando Claude Code guarda ahí un ajuste.

    proyectoprivado

    También vienen hooks de: plugins (hooks/hooks.json), el frontmatter de skills y subagentes, y los ajustes administrados de tu organización. Para ver todos con su origen, escribe /hooks: es un navegador de solo lectura.[2] Para quitar uno, borras su entrada del archivo.

    La regla

    Un hook corre con todos tus permisos. Léelo antes de pegarlo.

    Un hook command puede modificar, borrar o leer cualquier archivo al que tu usuario tenga acceso. La documentación pide revisar y probar cada comando antes de agregarlo.[2]

    • Pon comillas a las variables: "$VAR", no $VAR.
    • Usa rutas absolutas o "$CLAUDE_PROJECT_DIR" para llamar a tus scripts.
    • No toques archivos sensibles: .env, .git/, llaves.
    • Prueba el script a mano antes de conectarlo:
    echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh
echo $?

    Ese par de líneas viene de la sección de problemas comunes de la guía.[1]
