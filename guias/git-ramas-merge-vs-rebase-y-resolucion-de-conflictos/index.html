Ramas, merge vs rebase y conflictos

Dos ramas que se separaron se pueden juntar de dos formas: empalmando sus cintas con un commit nuevo, o recortando tus commits y volviéndolos a perforar encima del otro. Cuando ambas tocan el mismo renglón, git se detiene y te deja decidir.

2padres tiene un commit de fusión [2]
3versiones de un archivo guarda el índice durante un conflicto [5]
1regla para no romperle el trabajo a nadie con rebase [3]

01 · qué es una rama

41bytes

40 caracteres del hash SHA-1 del commit
+ 1 salto de línea
= una rama completa [1]

Una rama no contiene commits: apunta a uno

Una rama es un archivo con el hash del commit al que apunta; por eso crearla o borrarla no cuesta nada [1]. Lo que forma la historia son los commits, que guardan el hash de su padre. Cuando haces un commit nuevo, git solo reescribe esos 41 bytes para que la rama avance.

Para fusionar o hacer rebase, git busca el ancestro común: el último commit que las dos ramas comparten. Toca el tramo 3f1a9c2 del diagrama.

02 · dos formas de integrar

Mismo punto de partida, dos historias distintas

main avanzó con C3 mientras tú hacías C4 en feature. Ninguna es ancestro de la otra: las cintas divergieron. Este es el ejemplo del capítulo de rebase de Pro Git [3].

git merge feature

estando en main

  • Hace una fusión de tres vías con las dos puntas (C3, C4) y su ancestro común (C2) [2].
  • + Crea C5, un commit de fusión con más de un padre [2]. No toca ningún commit que ya existía.
  • − La historia queda con bifurcaciones: es el registro de lo que pasó, tal como pasó [3].

git rebase main

estando en feature, y luego git merge feature en main

  • Toma el cambio de cada commit tuyo desde el ancestro común y lo vuelve a aplicar, uno por uno, encima de main [4].
  • + Historia en una sola línea; el merge que sigue es un fast-forward [3].
  • − C4′ es un commit nuevo con otro hash: rebase abandona los commits existentes y crea otros parecidos pero distintos [3].

El contenido final es el mismo: el snapshot de C4′ es idéntico al de C5. Lo que cambia es la forma de la historia [3]. Pro Git lo resume así: haz rebase de tu trabajo local antes de compartirlo, y nunca de algo que ya empujaste [3].

04 · anatomía de un conflicto

Quién es ours depende de la operación

Main cambió timeout de 30 a 60 y tu commit lo cambió a 45; los dos agregaron retries = 3. Estás en feature y quieres traer main.

En un merge, ours es tu HEAD y theirs lo que fusionas [5]. En un rebase los lados se invierten: ours es la serie ya reaplicada, que empieza en main, y theirs es tu commit [4].

05 · resolver un conflicto

De CONFLICT a commit de fusión en seis pasos

Ahora en main fusionas feature. Git no crea el commit de fusión: pausa el proceso hasta que resuelvas [2]. Mira cómo cambian la cinta, el índice y el archivo en cada paso.

    
        
    
      
    
      
    
        
        
        
    Paso 1 de 6
    
      
    
      
    Si fuera un rebase, el cierre es git rebase --continue y git sigue con el siguiente commit; si te arrepientes a la mitad, git merge --abort o git rebase --abort regresan al estado anterior [4] [6].
    
    
    
  
    

  
  
    
    
    06 · la regla
    
    
    No hagas rebase de commits que existen fuera de tu repositorio y sobre los que otros pudieron basar su trabajo. [3]
    
    
    
      
      
    
        
    Si tus commits ya estaban en el servidor y alguien construyó encima, el rebase deja su trabajo colgando de commits que ya no existen allá. Al fusionar, va a tener que rehacer la integración, y si vuelve a empujar, los commits viejos regresan al servidor [3].
    
        
    
          
    Si de verdad tienes que reescribir algo publicado (por ejemplo, tu propia rama de pull request), usa:
    
          
    $ git push --force-with-lease
    
          
    Solo sobrescribe si la rama remota sigue apuntando a donde la viste la última vez; si alguien empujó algo mientras hacías rebase, el push falla en lugar de borrar su trabajo [7]. Ojo: un git fetch automático en segundo plano anula esa protección [7].
    
        
    
      
    
    
    
  
    

  
  
    
    
    07 · caja de herramientas
    
    
    Lo que conviene tener a mano antes del próximo conflicto
    
    
    
      
    
        
    Configura una vez
    
        
    Tres ajustes globales que cambian cómo se ven y se repiten los conflictos.
    

    # bloque con la versión original
$ git config --global merge.conflictStyle zdiff3
# recordar cómo resolviste cada conflicto
$ git config --global rerere.enabled true
# pull con rebase en vez de merge
$ git config --global pull.rebase true
    
        
    zdiff3 es como diff3, pero saca del bloque los renglones iguales en ambos lados [9]. rerere significa «reuse recorded resolution»: si el mismo conflicto vuelve a aparecer, git lo resuelve como la vez anterior [8]. pull.rebase hace que git pull reaplique tus commits locales encima de lo que bajas [3].
    
      
    
      
    
        
    Salir sin daño
    
        
    git merge --abort intenta reconstruir el estado previo a la fusión [6]. git rebase --abort regresa tu rama a como estaba [4].
    
      
    
      
    
        
    Seguir o saltar
    
        
    En un merge, git commit y git merge --continue hacen lo mismo [5]. En un rebase: --continue tras el git add, o --skip para descartar ese commit [4].
    
      
    
      
    
        
    Ver cada lado por separado
    

    $ git ls-files -u              # las entradas :1 :2 :3
$ git show :1:config.ini      # la base
$ git checkout --theirs config.ini
$ git mergetool                # herramienta visual
$ git log --graph --oneline --all
    
        
    git mergetool abre una herramienta visual que te lleva conflicto por conflicto [2]. Recuerda que en un rebase --theirs es tu commit [4].
